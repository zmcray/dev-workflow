# Chunks, tiers, wizards and landing groups

For `/packets`, `/factory`, and any plan with 3 or more Implementation Units.

## Chunks and tiers

Work reaches the build loop as **chunks**: one issue, one commit, well under an hour of agent time, about 5 files and 300 changed lines, 1-4 machine-checkable acceptance checks. When planning (`/ce-plan` or native), size Implementation Units to that bar and give each an honest `Files` list... that list becomes the chunk's **file scope**, a fence the building agent may not leave. Two chunks whose file scopes overlap get a `blocked by` edge; chunks with disjoint scope and no edge may be built at the same time by different agents (merges stay one at a time). Each chunk carries exactly one `tier:*` label for how hard it is to get right: `tier:mechanical`, `tier:moderate`, or `tier:judgment`. The dispatcher maps tier to a model; **never write a model name in an issue, plan, or packet.** Each chunk also answers a fifth question: **can it finish with nobody at the keyboard?** If any step needs a person present (a human looking at images or screens to judge them, credentials / 2FA / App Store or console clicks, a physical device, a taste call, an outside party), the chunk carries `gate:human` and its packet's `Human gate:` line says exactly what the person must do and when. Everything else is hands-off by default (no label). Overnight runs never pull `gate:human` or `ops` issues; those are day-shift work, batched for the morning. **Chunking is automatic, not a step to remember:** whenever a plan lands in `docs/plans/` with 3 or more Implementation Units (or any unit over the bar) for a Linear-tracked issue, cut it into chunks before building or ending the session... on Claude Code run `/packets`; on other harnesses do the same work natively. A goal run does this by itself (see `goal-runs.md`). Smaller plans are already a chunk: just add the `tier:*` label and file scope. A chunk whose issue already carries a build packet pointing at a plan unit is executed as written... do not re-plan it.

**Wizards for human procedures.** A `gate:human` step is one of two kinds. A **procedure** is clicking, copying and pasting only the person can do: keys or secrets from a vendor site, a dashboard or console setting, App Store Connect, applying a prod migration, account or device setup. A **judgment** is looking and deciding: screens or images, a taste or naming call, an outside party. The packet's `Human gate:` line starts with `procedure:` or `judgment:`. Every procedure gets a **wizard**: a guided bash script written with the `wizard` skill, saved as `scripts/wizards/<ISSUE-ID>-<slug>.sh`, committed, and linked from the issue with one line, `Wizard: bash scripts/wizards/<file>.sh`. The person runs it; an agent never does. A judgment gets no wizard and stays a one-line ask on the morning checklist. Unattended, skip the skill's confirm-the-stages step and list the stages in the issue comment instead; where the exact screen path is not known from the repo or the vendor's docs, the stage says so and links the docs, never invented clicks. `/factory` writes missing wizards at the start of each night; an agent that parks on a procedure mid-build writes its wizard before moving on. A wizard PR is a docs PR (`build.md` > Discipline > Commits): it names no issue ID anywhere, and its URL goes on the issue as a comment.

**Landing: group PRs.** A chunk is the unit of work and review; a **group PR** (one landing group) is the unit of CI and merge. Paying a full CI run per chunk multiplies CI time by the chunk count for review benefit a per-commit review already gives. So:

- **Group.** Consecutive chunks of one epic on one `blocked by` chain land together: one branch, one commit per chunk (conventional message with that chunk's issue ID), one PR. Cap a group at about 4 chunks or ~800 changed lines. `/packets` writes the grouping into each packet as a `Lands in:` line and into the plan's `## Chunks` table.
- **Build.** The agent builds the group's chunks in order on the one branch, runs each chunk's focused tests locally before committing, and opens the PR after the last chunk. CI runs once for the group.
- **Land alone.** A chunk ships in its own PR when it hits the escalation list (auth, sessions, tokens, RLS or grants, migrations, deletion or export, payments, outbound fetch) or carries `gate:human`, so it can be reviewed and reverted alone.
- **Merge.** Group PRs rebase-merge (`gh pr merge --rebase --delete-branch`) so every chunk stays one commit on the default branch and one `git revert` undoes one chunk. Single-chunk PRs squash-merge. If a repo disallows rebase merges, enable them in its settings.
- **Fail.** A red group PR is fixed on the branch. Per-chunk commits make the culprit easy to find; never merge part of a group.
